# build-rite

Claude Code harness. Copied as `.claude/` into project repos via `sync.sh`.
Project-specific context → project-root `CLAUDE.md` (generated by `/br-init`)

## Interaction rules

- Bullets > prose. Show progress between phases. Local edits don't need a confirmation; posting does (below).
- Analysis commands (review, health): understand → checkpoint → analyze → output.

## Input parsing (shared across commands)

`$ARGUMENTS`: Path → Read as context · Text → scope/problem · None → auto-scope or ask

## Workflow

- CLAUDE.md is the knowledge container — `/br-init` generates it; update after significant refactors
- Issues are the task system — batch related issues into PRs
- Refactor in chains — small focused steps, each its own commit
- `/br-plan` (read-only) → `/br-impl` (branch, code, verify, PR)
- `/br-review` before merge — severity-tiered, no auto-edits
- `/br-health` periodic project review — findings → docs + issues
- `/br-diagnose` when the question is *what/why/how much* (incident, capacity, cost, data quality) — read-only, ends in an answer not a PR

## External tools and libraries

For unfamiliar or recently-changed APIs: check official docs before implementing. Do not guess.
Prefer an installed CLI or API over browser automation — check (`command -v <tool>`, `<tool> --help`) before concluding there isn't one.

## PDF handling

When asked to read, summarize, or extract from a `.pdf`, prefer `markitdown` over reading the raw file:
- If `markitdown` is on PATH: `markitdown '<path>.pdf' -o "${TMPDIR:-/tmp}/<name>.md"`, then work from that `.md` — never write it next to the PDF, where it can overwrite a same-named file.
- If it's not available: ask whether to use it (`uv tool install markitdown`) or read the PDF directly.
- No OCR — if output is empty or garbled, the PDF is scanned/image-based. Fall back to reading the PDF directly and say so.

## Enforcement

- **Lean code** — follow the ponytail plugin (a prerequisite): smallest complete change, reuse the codebase / native features / popular libraries before writing new code. If ponytail isn't installed, say so once.
- **Scope discipline** — only modify what was asked. Don't expand to adjacent files, infra, or configs unless explicitly requested. State the scope (in/out) in one line and proceed; stop to ask only when it is genuinely ambiguous.
- **Confirmation before posting** — never post review comments, create issues, push commits, or run `terraform apply` without explicit user approval. Show the exact content/command first, wait for "go," then execute. Conversational analysis and local edits don't need this gate.
- `git add <explicit files>` only (deny rules block `git add -A` / `.`); use the project's package manager. Update a stale branch by merging its base — never rebase.
- No build-rite attribution in git artifacts — never expose `br-`, `build-rite`, or harness internals in commit messages, PR titles/bodies, or ticket comments. Conversational references to `/br-*` commands are fine.
- **Approval means execute** — once the user says go, run it yourself. Hand back only when you can't (interactive auth
  like SSO/MFA, a prompt-driven TUI, a credential you don't hold): say why in one line and suggest `! <command>`.
- **Git push blocked** — if push fails with a permission error, report it and stop. Do not retry; the user pushes manually (push only — not other commands).
- **Numbers carry provenance** — every figure states source, filter, time window, aggregate (min/max/p95/mean — never
  default to mean silently) and exclusions. Separate observed from derived, label estimates with a range, and when two
  sources disagree, report both and say which you trust.
- **Worktree paths** — always use absolute paths or `git rev-parse --show-toplevel` for hook and script path resolution. Never use relative paths in worktree contexts.
- **Parallel workers** — each worker gets its own worktree, branch, and files no other worker touches. The orchestrating
  session owns commits and pushes, and the user's instructions go to it, not to a worker.
- **No `cd` in Bash** — the working directory doesn't persist and `cd` can trigger permission prompts.
  Use `git -C <abs-path>`, tool-native flags (`make -C`, `uv --directory`, `terraform -chdir`), or absolute paths
  in the command itself. If a tool has no such flag, run it from a subshell: `(cd <abs-path> && <cmd>)`.

## Auto mode boundaries

Auto mode covers: local edits, running tests/builds, exploration, analysis, choosing between equivalent implementation approaches.

Auto mode does NOT override:
- **Skill checkpoints** — explicit `⏸ Checkpoint:` markers in skill templates are designed gates, not routine prompts. Stop and wait, regardless of mode.
- **Externally-visible actions** — posting PR comments, pushing, messaging, creating issues, `terraform apply`. Per "Confirmation before posting" above.
- **Edits on branches/PRs you don't own** — before any Edit/Write on the working tree, detect ownership: `gh pr view --json author -q .author.login` vs `gh api user -q .login`. If the branch has an open PR by someone else: review-only, no writes — findings go to conversation, not files. No PR yet → your branch.

## Verify before reporting

Before claiming done: re-fetch ground truth. Don't trust prior tool output as the final word.
- Issue/PR closed? → `gh issue view` / `gh pr view` to confirm state
- Applied/deployed? → re-run plan/build; expect zero diff
- Behavior fixed? → exercise the user-visible path, not just the unit test
Report what you verified, not just what you did.

## Tone & output style

- Lead with a tight summary; persona-target the audience
- Bullets > prose. No bombast ("wall of N findings", "comprehensive analysis")
- Ask before exhaustive lists. For long plans or docs, show a one-screen outline first (what one item is — feature,
  story, task; scope areas; exclusions) and wait for OK before drafting
- Don't duplicate content across files — reference the canonical source

## Human-facing output

Anything leaving this session — Slack, tickets, PR descriptions, artifacts, docs, exec summaries — is written
for a reader who wasn't here. Terse internal shorthand is fine in conversation, not in shared output.

- **Plain language.** "The flag is set, so this user won't be synced" — not "Flagged poison row 9423 via SQL → flag-setter unblocked."
- **No compressed notation.** No `→` chains, no `A/B/C` shorthand, no stacked qualifiers standing in for a sentence.
- **No invented vocabulary.** Use the team's existing names for things. Don't coin a concept (a new "lane", "tier", "mode")
  to explain a finding — if a new idea is genuinely needed, say so and get agreement before building on it.
- **Text before artifact.** Deliver the plain-text version in conversation first and wait for it to be accepted.
  Artifacts, Notion pages, and Slack drafts come after, never instead.
- **Match the audience.** A Slack update is 5 lines and skimmable. A handoff doc is complete. Ask which if unclear.
- **Conservative claims.** Never overstate a fix or finding. Say what isn't verified.

## Check output template

When reporting verification results, use this shape (omit rows that don't apply):
```
Checks
  Lint    ✓ clean          (or ✗ N errors — <first error>)
  Types   ✓ clean          (or ✗ skipped — no type check configured)
  Tests   ✓ N passed       (or ✗ N failed — <test name>)
  Status  ✓ healthy        (or ✗ unhealthy — <response>)
  Deps    ✓ no advisories  (or ✗ N advisories — <ids>)
```

**Deps** audit — run whenever a manifest or lockfile changes, and in every health review: `uv audit --frozen` (uv) ·
`uvx pip-audit -r requirements.txt` (plain pip) · the lockfile's `npm`/`pnpm`/`yarn audit --audit-level=high` (Node) ·
plus open Dependabot alerts: `gh api "repos/{owner}/{repo}/dependabot/alerts?state=open" --paginate`. An unreachable
advisory with no fix → `--ignore-until-fixed <id>` with a written reason, never a silent skip.

## Plugin guardrails

**pr-review-toolkit** — never auto-invoke any agent proactively. Never run `/review-pr all` unprompted. Avoid `code-simplifier` — it auto-edits without confirmation.

## References

**Secret patterns** — scan diff and refuse to stage/commit if any match: `sk-`, `-----BEGIN`, `ghp_`, `AKIA`, `xox`, or `password|secret|token|api_key =` with a literal string value.

**Commit message format** — scale to change size:
```
<type>: <imperative summary>  (≤72 chars)

Problem:   <what was broken or missing>
Solution:  <what changed and why>
Testing:   <how to verify>
```
Trivial fix → subject only. Large/multi-area → add `Ticket:`, `Assumptions:`, `Follow-up:` as needed.
